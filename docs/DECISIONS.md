# Decision log

Decisions made where the build prompt was ambiguous. Simplest option consistent with the spec was chosen.

| # | Area | Decision | Why |
|---|------|----------|-----|
| 1 | Money | Stored as `BigInt` centavos (columns end in `Cents`). Domain code uses `number` centavos (safe to ±₱90 trillion). Percentages are `Float` (e.g. `12.5` = 12.5%). | Integer centavos avoid float drift; `Int` overflows at ₱21M. |
| 2 | Sessions | Auth.js uses a JWT cookie that carries only an opaque `sessionToken`; the `Session` table is the source of truth and is checked on every request (`getCurrentUser`). | Auth.js database sessions don't work with the Credentials provider (needed for the bootstrap Admin). This still gives DB-stored, revocable sessions so Admin "force sign-out" works instantly. |
| 3 | Password login | Only the bootstrap Admin (role key `ADMIN` with a password hash) can use password login, and only while `Settings → passwordLoginEnabled` is on. `DEMO_PASSWORD_LOGIN=true` lets seeded demo users sign in with the bootstrap password for demos/E2E tests; it must be `false` in production. | Spec: fallback for bootstrap Admin only; demos/E2E need per-role sign-in without Entra. |
| 4 | Microsoft tokens | Graph scopes are requested at SSO sign-in, so signing in with Microsoft also connects the mailbox/calendar. Refresh tokens are encrypted with AES-256-GCM (`ENCRYPTION_KEY`). | One consent step; fewer moving parts. |
| 5 | Permissions | Permissions are a code-defined catalog (`src/lib/rbac/permissions.ts`); roles store a `String[]`. Admin role is `"*"` and cannot be edited. | Matrix UI needs a fixed set of resources/actions; adding a permission is a code change anyway. |
| 6 | Default grants | Sales Manager gets `transactions:cancel` and `commissions:approve` by default (they own sales and commissions). `price_lists:update` and `commissions:release` are **not** granted to any non-Admin role by default — Admin grants them deliberately. | Spec requires these to be separate permissions; finance-sensitive actions default to Admin-only. |
| 7 | Deleting users | Users are soft-deleted (email rewritten so it can be re-invited) to preserve audit history. | Referential integrity of audit/timeline records. |
| 8 | Rate limiting | In-memory fixed-window limiter (single `web` container). | Simplest; documented swap path if scaled out. |
| 9 | CSP | Nonce-based CSP set in middleware (`strict-dynamic`). `style-src 'unsafe-inline'` is allowed because Recharts/Radix set inline styles. | Strict scripts, practical styles. |
| 10 | Forms | Zod schemas in `src/lib/validation/schemas.ts` are used by both react-hook-form (client) and the `action()` wrapper (server). Forms submit raw strings; schemas transform (pesos → centavos, `YYYY-MM-DD` → Date) identically on both sides. | One schema, two enforcement points. |
| 11 | Dates | Date-only fields (`@db.Date`) are stored at UTC midnight and formatted in UTC; timestamps are formatted in `Asia/Manila`. | Prevents off-by-one day shifts. |
| 12 | Prices | `Unit.listPriceCents` / `ParkingSlot.listPriceCents` always hold the *current* price. Every change (single item, % across the board, or import) creates a new `PriceList` version with per-item previous/new prices. Versions effective today or earlier apply immediately; future-dated versions are applied by the `price-lists.apply` worker job at 00:05 Manila. | History is kept, and reads stay simple. |
| 13 | Inventory transitions | `AVAILABLE→RESERVED` is allowed directly (walk-in reservation without a prior hold). Reserving an `ON_HOLD` item requires the reservation to reference that hold (enforced in Phase 4). `RESERVED→SOLD` happens when the Contract to Sell is signed. | Matches the lifecycle in the spec while allowing same-day reservations. |
| 14 | Import | Inventory import matches rows by `code` within the chosen development. New items need a price; changed prices on existing items need `price_lists:update` and are saved as one new price list version. Sections must already exist. | Prevents accidental price changes through bulk import. |
| 15 | Computation math | Order: promo discount (% then fixed) on list price → spot-cash discount → NSP → VAT per item (exempt at/below the per-unit-type threshold; parking optionally always VATable) → misc. fees as % of NSP (optionally inside TCP) → TCP. Reservation fee is deducted from the down payment. Spot-DP discount reduces only the DP. | Common PH developer practice; every rate/threshold is a Setting. |
| 16 | VAT exclusive by default | `vat.pricesIncludeVat = false`: VAT is added on top of NSP. If true, VAT is shown for information and not added. | Must be confirmed by Citrineland finance. |
| 17 | Schedule | Generated once at reservation from the frozen computation. Payments are applied oldest-due-first; `ScheduleItem.paidCents` is recomputed on every payment/void. Bank/Pag-IBIG balance is one "loan takeout" line due the month after the last DP; in-house financing generates a full amortization table. | Simple, auditable, and reproducible. |
| 18 | SOLD | Inventory moves RESERVED → SOLD when the transaction reaches CONTRACT_SIGNED. | Contract to Sell is the binding sale. |
| 19 | Maceda inputs | "Years of installments" = full years of monthly installment lines (DP/deferred/amortization) fully paid; "total payments" = all non-voided payments incl. reservation fee. Spot cash and bank/Pag-IBIG-financed sales after takeout are flagged "not applicable". The snapshot is stored on the transaction at cancellation. | Indicative only, for legal/finance review. |
| 20 | Transfers | A transfer creates a new transaction (new unit and/or buyer), re-points payments and documents to it, forfeits unreleased commission on the old one and creates a new ledger. | Keeps each transaction's history immutable. |
| 21 | Concurrency | Reservations lock all requested inventory rows with `SELECT … FOR UPDATE` in a deterministic order inside one DB transaction; the loser of a race gets "no longer available". Covered by `tests/integration/reservation.test.ts`. | Prevents double-selling. |
| 22 | Commission rate precedence | Broker's personal override % → most specific active rule (dev+brokerage → brokerage → development → global) → brokerage default % → `defaultCommissionPct` setting. Without a rule, default tranches are 50% at 20% of TCP collected and 50% at full DP. Direct sales (no broker of record) have no ledger. Independent brokers receive 100% (no brokerage split). | Spec lists rules per development and/or brokerage; precedence had to be chosen. |
| 23 | Tranche automation | Tranches move NOT_DUE→DUE automatically after every payment/void/status change (and back to NOT_DUE if a voided payment un-reaches the milestone, unless already approved/released). Cancellation/transfer forfeits NOT_DUE/DUE/APPROVED tranches; RELEASED ones trigger a "consider clawback" notification and clawback is a manual negative adjustment. | Matches §4.8. |
| 24 | Exports | Reports are defined once as `ReportTable` (columns + rows) and served by `/api/export/<report>?format=csv|xlsx` (requires `reports:export` plus the report's own permission; every export is audited). | One export path for all reports. |
| 25 | Automation execution | Domain events (`lead.created`, `lead.stage_changed`, `transaction.reserved`, `transaction.status_changed`, `payment.recorded`, `email.received`) are enqueued to pg-boss and handled by the worker (`automation.dispatch`). Time-based automations run as cron scanners. Built-ins are rows in `AutomationRule` with a `builtInKey` (toggle + JSON config); custom rules use the same table. | Business operations never block on automations; everything is retryable and visible in Admin → Background jobs. |
| 26 | Always-on rules | Schedule/checklist generation at reservation, auto-release of expired holds, tranche DUE marking and broker auto-EXPIRED are business rules and always run; their *notifications/tasks* are the toggleable part. | Toggling a notification should never corrupt inventory or commission state. |
| 27 | Web leads | `POST /api/public/leads`: per-IP rate limit (Settings), Cloudflare Turnstile CAPTCHA (skipped if no secret is configured), hidden honeypot field, CORS allow-list, UTM capture (`utm_campaign` ↔ `Campaign.code`). If an open lead already has the same email or mobile, the inquiry is logged on that lead instead of creating a duplicate. A hosted iframe form lives at `/f/lead`. | Keeps the pipeline clean of web duplicates. |
| 28 | Sequences | Steps are sent from the lead owner's Outlook (falls back to the enrolling user). Open tracking isn't available via Graph, so performance shows sends, replies and reply rate. Every email includes an unsubscribe link (`/unsubscribe/<token>`) that sets `doNotEmail` and stops all sequences. | Delegated Graph permissions only. |
| 29 | Notification email | Opted-in users get their notifications emailed *from their own mailbox to themselves* (delegated `Mail.Send`), avoiding an application-level send permission. | Least privilege. |
| 30 | Data privacy | Consent checkbox + timestamp on leads/clients (required on the web form). KYC documents need `kyc:view`; every download (and denied attempt) is audited. Admin → Data privacy exports a client's data as JSON or anonymizes them (personal data replaced, KYC files removed, financial records kept for retention); blocked while the client has an active transaction. | RA 10173 spirit with accounting retention. |
| 31 | Backups | Managed Database backups are relied on when using DO Managed PostgreSQL. The Compose `backup` service (profile `localdb`) does nightly `pg_dump` → Spaces with 30-day retention for self-hosted Postgres. | Spec §10. |
| 32 | Tests | Integration and E2E tests run against the seeded database and create (then cancel) their own transactions; run them against a disposable database, not production. | Realistic coverage of locking and UI flows. |
| 33 | Free demo hosting | Before production is approved, the app runs free on Render (Docker web service) + Neon (Postgres). Because free tiers have no worker container and no persistent disk, `RUN_WORKER_IN_WEB=true` starts the pg-boss worker inside the web process (via `src/instrumentation.ts`) and `STORAGE_DRIVER=database` keeps uploaded files in Postgres. `scripts/start-web.sh` migrates and seeds (idempotent) on every start. Production keeps the separate worker and Spaces, with only config changes. | No infrastructure spend until the go-signal; same code path as production. |

## Items needing Citrineland's input

These are configurable in the app but the values in the seed are placeholders:

1. **VAT treatment** — whether list prices include VAT, the current BIR residential VAT-exemption thresholds per unit type, and whether parking is always VATable (Admin → Settings → VAT).
2. **Misc. fees / other charges** — percentage and whether it is part of the TCP (Settings).
3. **Default loan rates and terms** for bank, Pag-IBIG and in-house estimates (Settings).
4. **Payment schemes** per development: reservation fees, DP %, DP months, spot-DP discount, in-house rate/term (Admin → Payment schemes).
5. **Commission rules** — rate, NSP vs TCP basis, brokerage/agent split, release tranches and milestones, per development/brokerage (Admin → Commission rules). Who receives payment (brokerage only vs split) also affects the future NetSuite vendor bills.
6. **Documentation checklist** — exact required documents, due days, and which apply to bank / Pag-IBIG / in-house buyers (Admin → Document checklist).
7. **Pipeline stages, lost reasons and lead sources** (Admin → Pipeline stages, Picklists).
8. **Hold duration** (default 48h) and **parking ownership rule** (default on).
9. **Quotas** per staff/broker/brokerage.
10. **Legal review** of the Maceda Law helper wording and of the computation disclaimer text.
11. **Branding** — replace the logo placeholder (`src/components/app/logo.tsx`, `src/config/brand.ts`).
12. **Microsoft 365** — tenant ID, app registration, internal email domains for capture filtering.
13. **NetSuite** — open questions listed in `docs/NETSUITE_INTEGRATION_PLAN.md`.
